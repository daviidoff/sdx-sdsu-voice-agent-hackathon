## Changes made and retested

1. **New location before local guidance.** `propose_location` records a reported place and clears the old current instruction and map coordinates. The assistant reads it back and waits for confirmation. A pending proposal cannot resolve before a subsequent caller transcript turn. Confirmation applies the new zone while preserving needs and event history. Existing request/revision guards reject delayed old results.
2. **Distinguish place, destination and instruction area.** A planned destination does not change current position. Being outside an evacuation area does not erase an applicable warning or monitoring instruction. Own current location and a relative's last-known location remain separate; the intermittent TC-21 failure above is not resolved.
3. **Preserve explicit facts.** Functional barriers such as inability to use stairs go into the mobility field as well as the operator message. Negative transport answers are saved. Generic requests for help remain unspecified instead of becoming inferred transport requests. Relevant needs, hazards and offers can reach the existing inbox without pretending that dedicated structured workflows already exist.
4. **Prioritize urgent danger and honest action status.** Immediate-danger reports interrupt intake and receive the configured emergency-service referral. Messages require an actual received receipt before a successful-send claim. Inbox receipt does not mean a responder accepted the case, a vehicle was dispatched, or a facility has capacity.
5. **Correct evaluator errors.** The adapter supports all six production client tools and the immediate operator-message turn path. It waits for the provider's explicit response-completion event instead of an arbitrary idle gap. Speech assertions check advice rather than demanding arbitrary fixture reference words; independent zone/version/fact checks remain. One ambiguous group-size script was made explicit about the total including the caller.
6. **Verify the real dashboard.** Chromium runs the production React UI against isolated application state. Checks include visible map dimensions, settled animation, caller-marker alignment with the named synthetic place, facts/instruction convergence, reload and operator-inbox rendering. An immutable source/build snapshot prevents unrelated edits from changing the test halfway through.

## What remains before stronger claims

The next reliability improvement should address TC-21 through an explicit intake-state/fallback design and a broader repeated paraphrase matrix, rather than treating another prompt example as proof. No wrong-zone advice was observed in the final suite, but a single successful run cannot establish reliability. Review also found occasional compound questions and an off-topic joke before redirection; the short-question and focus policies are not fully enforced by current automatic assertions.

The 20 blocked cases cover missing or incomplete capabilities: incident scoping; published-order expiry/revocation; emergency-service acceptance; structured hazards, communication needs, dependents, medical equipment, supplies, missing people and resource offers; willingness versus ability; commitments/cancellations; verified arrival and understanding; withdrawn-transcript reconciliation; and additional capacity-fixture variants. An inbox message helps surface these needs but does not implement those lifecycles.

Synthetic coordinates and polygons verify the application's mapping flow, not live address accuracy. Audio, transcription, telephone networks, real emergency dispatch, provider acceptance and real-world shelter/vehicle capacity were not exercised. The suite is an engineering evaluation, not a validated emergency-dispatch protocol.
